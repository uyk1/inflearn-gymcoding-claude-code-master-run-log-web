# ROADMAP: Run Log

## 개요

- **목적**: `docs/PRD.md`에 정의한 기능을 어떤 순서로 구현하고 검증할지 정리합니다.
- **PRD와의 차이**: PRD는 "무엇을 만들 것인가"(기능, 기술 스택, 데이터 구조, MVP 범위)를 정의합니다. 이 로드맵은 "어떤 순서로 만들 것인가"(Phase, 작업, 소요 시간, 완료 기준)를 정의합니다. 기능 자체의 명세는 PRD를 기준으로 합니다.
- **개발 원칙**: 골격 → 공통 모듈 → 핵심 기능 → 추가 기능 → 최적화 및 배포 순서로 진행합니다. 공통 계층(Notion 데이터 계층, 타입) 없이 화면부터 만들지 않습니다.
- **소요 시간**: 1인 개발 기준의 대략적인 추정치(일 단위)이며, 실제 진행에 따라 조정합니다.
- **상태 표시**: ✅ 완료(확인 완료된 항목만), 진행 중, 미착수로 구분합니다.

## Phase 2: 공통 모듈 (Notion 데이터 계층, 타입, 공통 컴포넌트)

**상태**: 진행 중

### 할 작업

- ✅ Notion 클라이언트 래퍼 작성 (서버 전용, `NOTION_API_KEY` 사용) (PR #5, `server-only` 가드 PR #11, 키 번들 미노출 확인)
- Repository 계층: `dataSources.query` 호출, 페이지네이션 처리
- Service 계층: 소요 시간 파싱(`mm:ss`, `h:mm:ss` → 초), 평균 페이스 계산(초 ÷ km → `mm:ss`), 거리 0 또는 시간 없음 시 `-` 처리
- ✅ DTO 매핑: 필드명 상수를 한 파일에 모아 노션 필드 변경 시 한 곳만 고치도록 함 (`lib/notion/properties.ts` 한 곳, PR #5)
- ✅ 잘못된 행 처리: 파싱 실패 행은 목록에서 제외하고 로그 남김 (실제 노션 TEST 행으로 확인, 2026-10-30)
- ✅ 공통 응답 형식과 에러 응답 형식 정의 (`lib/api/response.ts`, `lib/errors.ts`, PR #5)
- ✅ 타입 정의 (러닝 기록 도메인 타입, API 응답 타입) (`RunRecordDto`, `ApiResponse`, PR #5)
- 공통 컴포넌트 최소 세트 (기록 카드, 빈 상태, 에러 표시 등 Phase 3에서 쓸 것만)

### 왜 이 순서인지

목록·상세·통계 모두 같은 데이터 계층과 파싱 규칙을 씁니다. 여기서 먼저 정해 두어야 화면마다 파싱 로직이 흩어지지 않습니다. PRD 9장의 리스크(필드 변경, 입력 오류) 대응도 이 단계에서 구조로 잡습니다.

### 예상 소요 시간

2일

### 완료 기준

- ✅ 화면 없이 서버 코드로 노션 데이터를 조회해 정규화된 기록 배열을 얻을 수 있다 (2026-10-30 확인, 실제 노션 행이 서비스를 거쳐 정규화되어 목록에 표시됨. 화면을 거친 확인).
- `mm:ss`, `h:mm:ss` 파싱과 페이스 계산에 대해 대표 입력(정상, 잘못된 초 `75`, 빈 값, 거리 0)의 결과를 직접 확인했다.
- ✅ 파싱 실패 행이 목록에서 빠지고 서버 로그에 남는다 (2026-10-30 확인, 날짜 없음과 `75:99` 행이 제외되고 로그에 페이지 ID 기록).
- ✅ 노션 API 키가 클라이언트 번들에 포함되지 않는다(`NEXT_PUBLIC_` 미사용 확인) (2026-10-30 확인, 빌드 산출물에서 키 문자열 0건).
- 에러 응답이 공통 형식을 따른다.
- ✅ `npx tsc --noEmit`과 `npm run lint`가 통과한다 (2026-10-30 확인).

## Phase 3: 핵심 기능 (기록 목록·상세)

**상태**: 미착수

### 할 작업

- 기록 목록 화면: 날짜순 정렬, 기간 필터(예: 이번 주, 이번 달, 전체)
- 기록 상세 화면: 제목, 날짜, 거리, 소요 시간, 페이스, 장소, 강도, 메모, 태그 등 전체 필드 표시
- 상세 화면의 노션 원본 링크
- 홈 화면: 최근 기록 요약, 이번 주 총 거리 (PRD 5장)
- 모바일 레이아웃 확인 (가로 스크롤 없음, PRD 8장)

### 왜 이 순서인지

목록과 상세는 Phase 2의 데이터 계층만 있으면 만들 수 있고, 사용자가 가장 먼저 쓰는 가치입니다. 통계는 같은 데이터를 집계하므로 목록·상세가 맞게 나온 뒤에 만듭니다. 홈은 목록의 데이터와 요약 함수를 재사용하므로 이 단계에 둡니다.

### 예상 소요 시간

2일

### 완료 기준

- 목록에 Notion 기록이 날짜순으로 나오고, 기간 필터가 동작한다.
- 목록의 각 항목을 누르면 상세 화면으로 이동하고, 상세에 PRD 4장의 필드가 표시된다.
- 상세의 노션 링크가 해당 기록 페이지를 연다.
- 빈 값이 있는 기록(메모 없음, 장소 없음)도 깨지지 않고 표시된다.
- 모바일 폭(약 360px)에서 가로 스크롤이 없다.
- 노션에서 기록을 추가하면 새로고침 후 목록에 반영된다.

## Phase 4: 추가 기능 (통계, PWA)

**상태**: 미착수

### 할 작업

**통계**
- recharts 설치 (shadcn `chart` 컴포넌트와의 호환은 구현 시 확인)
- 주간·월간 총 거리, 총 시간, 평균 페이스 추이 계산 (서비스 계층에 집계 함수)
- 통계 화면: 주간·월간 거리와 페이스 차트

**PWA**
- `app/manifest.ts` 작성 (앱 이름, `display: "standalone"`, 아이콘)
- 아이콘 세트 준비 (192·512 PNG, `apple-touch-icon`)
- metadata에 `apple-touch-icon` 연결
- 설치 안내: 안드로이드는 설치 버튼, 아이폰은 "공유 → 홈 화면에 추가" 문구

### 왜 이 순서인지

통계는 Phase 3까지의 기록 데이터를 집계하는 기능이라 그 뒤에 와야 합니다. PWA는 기능과 독립적이라 순서를 바꿔도 되지만, 기록 화면이 있어야 설치 후 실행 결과를 의미 있게 확인할 수 있으므로 뒤에 둡니다. service worker는 MVP 범위 밖입니다(PRD 6장).

### 예상 소요 시간

통계 2일, PWA 1일 (합계 3일)

### 완료 기준

- 통계 화면에서 주간·월간 총 거리와 평균 페이스가 수동 계산 값과 일치한다(샘플 기록 기준으로 최소 1건 대조).
- 차트가 라이트·다크 모드 모두에서 읽힌다.
- `/manifest.webmanifest`(또는 `app/manifest.ts` 결과)에 이름, `display: "standalone"`, 192·512 아이콘이 있다.
- `apple-touch-icon` 링크가 HTML에 포함된다.
- 데스크톱 Chrome 개발자 도구에서 manifest 항목에 오류가 없다.
- 설치 안내 문구가 안드로이드와 아이폰 각각에 맞게 보인다.

## Phase 5: 최적화 및 배포

**상태**: 미착수

### 할 작업

- ISR 캐싱 적용: `revalidate` 값 설정으로 노션 API 호출 수 줄이기 (PRD 7장 6단계)
- 페이지네이션과 rate limit 대응 확인 (PRD 9장)
- 프로덕션 환경 변수 설정 (배포 플랫폼에 `NOTION_API_KEY`, `NOTION_DATA_SOURCE_ID` 등록)
- 배포 및 배포 URL 확인
- 실기기 확인: 갤럭시(Chrome, Samsung Internet)와 아이폰(Safari)에서 홈 화면 추가 후 독립 창 실행 확인 (PRD 7장 7단계)
- 발견된 문제 수정

### 왜 이 순서인지

캐싱과 배포 설정은 기능이 모두 동작한 뒤에 조정해야 정확한 측정이 가능합니다. 실기기 확인은 실제 배포 URL에서만 PWA 설치가 되므로 배포 뒤에 합니다.

### 예상 소요 시간

1.5일 (캐싱·배포 설정 0.5일, 실기기 확인과 수정 1일)

### 완료 기준

- 배포 URL에서 목록과 상세가 열리고, 노션 키가 브라우저 소스에 노출되지 않는다.
- 노션 API 호출이 `revalidate` 주기 안에서 반복되지 않는다(서버 로그 또는 배포 환경 로그로 확인).
- 갤럭시(Chrome)와 아이폰(Safari)에서 홈 화면에 추가 후 주소창 없이 실행된다.
- 모바일 화면 가로 스크롤이 없다.
