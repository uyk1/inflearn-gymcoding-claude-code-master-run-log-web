# ROADMAP v2: Run Log 관리자 페이지

> MVP(v1) 로드맵은 [roadmaps/ROADMAP-v1.md](roadmaps/ROADMAP-v1.md)에 보관되어 있습니다.

## 개요

- **목적**: 노션 앱을 열지 않고 웹에서 러닝 기록을 안전하게 입력·수정·삭제하고, 입력 오류로 목록에서 제외되는 행을 없앱니다.
- **v1의 결과**: 읽기 전용 MVP가 2026-11-05에 완료되어 https://pjt-run-log.vercel.app 에 배포되어 있습니다. 기록 목록·상세, 주간·월간 통계, PWA 설치를 지원하며 노션 호출은 서버에서만 합니다.
- **PRD와의 관계**: v1 PRD 6장은 "로그인·인증"과 "웹에서 기록 입력·수정·삭제"를 MVP 제외 항목으로 정했습니다. v2는 이 둘을 범위에 넣으므로 PRD를 v2로 새로 작성하고 v1은 [prds/PRD-v1.md](prds/PRD-v1.md)에 보관합니다(Phase 0 결정). 기능 자체의 명세는 현재 [PRD.md](PRD.md)를 기준으로 합니다.
- **개발 원칙**: 인증 → 쓰기 계층 → 입력 → 수정·삭제 → 제외 행 고치기 순서로 진행합니다. 인증 없이 쓰기 기능을 배포하지 않습니다. 공개 조회(읽기 전용 키)와 관리자 쓰기(별도 키)는 노션 키와 코드 경로를 분리합니다.
- **소요 시간**: 1인 개발 기준의 대략적인 추정치(일 단위)이며, 실제 진행에 따라 조정합니다.
- **상태 표시**: ✅ 완료(확인 완료된 항목만), 진행 중, 미착수로 구분합니다. 직접 확인하지 않은 항목은 ✅를 쓰지 않습니다.
- **v1에서 넘어온 미확인·한계**
  - 갤럭시(Chrome, Samsung Internet) 설치와 안드로이드 "앱 설치" 버튼은 확인하지 않았습니다.
  - `lib/api/response.ts`의 응답 형식(`apiSuccess`, `apiFailure`)은 API 라우트가 없어 실제 응답으로 확인하지 못했습니다. Phase 2에서 다룹니다.
  - 상세 화면(`/runs/[id]`)은 목록 캐시를 거치지 않고 노션 전체 기록을 직접 조회해, 존재하지 않는 서로 다른 주소를 요청할 때마다 노션 호출이 생깁니다. 상세도 공유 캐시를 쓰도록 바꾸기로 했고(Phase 0 결정), Phase 2의 첫 작업에서 반영합니다.

## Phase 0: 준비 (PRD 갱신·결정)

**상태**: 미착수

### 할 작업

- PRD 변경 방식 결정: 기존 `docs/PRD.md`의 제외 항목(로그인·인증, 웹 입력·수정·삭제)을 고칠지, v2용 PRD를 새로 둘지 사용자가 정합니다. 결정 전에는 PRD를 수정하지 않습니다.
- 테스트 전략 결정: 현재 테스트 러너가 없습니다. 쓰기 기능은 위험이 커서 최소한 입력 검증 함수의 단위 테스트를 도입할지 정합니다(도입하면 새 패키지 승인 필요).
- 노션 키 분리 설계: 공개 조회용 읽기 전용 키는 그대로 두고, 관리자 쓰기용 키를 별도 환경 변수로 둡니다. 통합 권한은 필요한 만큼만 엽니다(읽기, 삽입, 수정).
- v1 알려진 한계 처리 방침: 상세 화면이 목록 캐시를 쓰도록 바꿀지(노션 호출 증폭 해소, 새 기록이 상세에서 최대 약 1분 늦게 열릴 수 있음), 형식 검사만 넣을지, 그대로 둘지 정합니다.
- 관리자 화면에서 제외된 행의 입력 원문을 보여 줄지 정합니다(PRD 4장은 공개 화면에서 원문을 숨기도록 했지만, 고치려면 관리자에게는 원문이 필요합니다).

### 왜 이 순서인지

관리자 페이지는 PRD가 제외한 범위를 다루므로, 요구사항과 안전 조건을 먼저 문서로 확정해야 이후 Phase의 완료 기준이 흔들리지 않습니다. 쓰기 키 분리와 테스트 방식은 Phase 2의 구조를 정하는 전제입니다.

### 예상 소요 시간

0.5일

### 완료 기준

- PRD 변경 방식이 정해지고 그에 따라 문서가 갱신되었다(사용자 승인 후).
- 테스트 전략, 노션 키 분리 방식, 상세 화면 처리 방침, 제외 행 원문 표시 여부가 이 로드맵 또는 PRD에 기록되어 있다.

## Phase 1: 인증

**상태**: 미착수

### 할 작업

- 인증 방식 결정(아래 "열린 질문과 리스크"의 비교표 참고)
- `/admin` 이하 보호: 미들웨어로 1차 차단하고, 페이지와 쓰기 동작에서 서버 측 세션을 다시 확인합니다. 미들웨어만 믿지 않습니다.
- 로그인·로그아웃 화면, 로그인 실패 횟수 제한
- 세션 쿠키 설정(HttpOnly, Secure, SameSite, 만료)
- 인증 관련 환경 변수: 이름만 `.env.example`에 추가하고 값은 `.env.local`과 Vercel 콘솔에만 둡니다.
- `security-checker` 점검

### 왜 이 순서인지

인증 없이 쓰기 기능을 배포하면 주소를 아는 누구나 노션 DB에 쓸 수 있습니다. 쓰기 계층과 화면은 보호할 대상이 있어야 의미가 있으므로 인증을 가장 먼저 둡니다.

### 예상 소요 시간

2일

### 완료 기준

- 비로그인 상태로 `/admin`에 접속하면 로그인 화면으로 이동한다.
- 비로그인 상태로 쓰기 동작을 직접 호출해도 서버에서 거부된다.
- 로그인 실패를 반복하면 제한된다.
- 세션 쿠키의 보안 속성을 직접 확인했다.
- 공개 화면(`/`, `/runs`, 상세, `/stats`)의 동작과 캐시는 달라지지 않았다.
- 인증 비밀값이 저장소와 클라이언트 번들에 없다.
- `npx tsc --noEmit`, `npm run lint`가 통과한다.

## Phase 2: 쓰기 계층

**상태**: 미착수

### 할 작업

- 상세 화면(`/runs/[id]`)이 `loadRunRecords()`의 공유 캐시에서 기록을 찾도록 바꿉니다(`lib/runs/load.ts`에 단건 조회 추가, 약 0.25일). 이때 `CLAUDE.md`의 "상세는 직접 조회" 문장과 README의 알려진 한계 절도 고칩니다.
- 쓰기 전용 노션 키를 별도 환경 변수(`NOTION_ADMIN_API_KEY`)로 읽는 서버 전용 모듈을 `lib/notion/admin/`에 만들고(`server-only`), ESLint `no-restricted-imports`로 관리자 영역 밖에서 이 모듈을 import하지 못하게 막습니다.
- `lib/notion/mapper.ts`의 읽기 함수(`readTitle`, `readDate` 등)를 공유 모듈로 분리해 관리자 단건 조회와 쓰기 검증에서 재사용합니다.
- `package.json`에 `test` 스크립트(`node --test`)를 추가하고 입력 검증 함수를 단위 테스트합니다. 테스트 대상 모듈은 `@/` 별칭 대신 상대 경로로 import하며 새 패키지는 설치하지 않습니다.
- Repository: 페이지 생성, 수정, 휴지통 이동
- 입력 검증(zod 4): 읽기 쪽 규칙을 공유합니다(`lib/notion/duration.ts`의 `parseDurationToSeconds`, `lib/notion/date.ts`의 `normalizeNotionDate`, 거리는 숫자).
- 입력 DTO와 쓰기 Service, 실패는 `AppError`로 변환
- 응답 형식(`apiSuccess`, `apiFailure`)을 실제로 사용하고 응답으로 확인합니다(v1에서 못 닫은 항목).
- 외부ID 필드(PRD 4장)로 중복 입력을 막는 방법 검토
- 노션 쓰기 검증은 사용자 확인 후 `TEST-` 행으로만 하고, 끝나면 휴지통으로 보내 `in_trash`를 확인합니다.

### 왜 이 순서인지

화면보다 쓰기 규칙을 먼저 정해야 입력 폼이 검증과 오류 처리를 중복해서 만들지 않습니다. 읽기와 같은 검증 규칙을 공유해야 "입력은 통과했는데 목록에서 제외되는 기록"이 생기지 않습니다.

### 예상 소요 시간

2.25일

### 완료 기준

- 화면 없이 서버 코드로 입력 DTO를 넘겨 노션 행을 만들 수 있고, 그 행이 공개 목록에 제외 없이 표시된다.
- 잘못된 입력(예: 소요시간 `12:5`, 존재하지 않는 날짜)은 쓰기 전에 거부되고 노션에 행이 생기지 않는다.
- 쓰기 키가 공개 읽기 경로의 모듈과 클라이언트 번들에 포함되지 않는다.
- 성공과 실패 응답이 `apiSuccess`, `apiFailure` 형식으로 확인된다.
- 서로 다른 존재하지 않는 id로 상세를 요청해도 노션 호출이 늘지 않는다(호출 계수로 확인).
- 관리자 영역 밖의 코드가 `lib/notion/admin/`을 import하면 lint가 실패한다.
- 입력 검증 단위 테스트(`node --test`)가 통과한다.
- `npx tsc --noEmit`, `npm run lint`가 통과한다.

## Phase 3: 기록 입력

**상태**: 미착수

### 할 작업

- `/admin/runs/new` 입력 폼: `useForm` + `zodResolver` + `Controller` + `Field`/`FieldError` 조합(CLAUDE.md의 폼 패턴)
- 모바일 우선 레이아웃, 소요시간 입력 보조(형식 안내)
- 제출 뒤 캐시 갱신: `revalidateTag("run-records")`와 홈·상세 `revalidatePath`
- 중복 제출 방지(제출 중 버튼 비활성, 필요하면 외부ID 활용)
- 제출 성공·실패 안내

### 왜 이 순서인지

폼은 Phase 2의 검증과 쓰기 계층 위에 얹는 얇은 화면입니다. 캐시 갱신까지 같이 해야 입력한 기록이 공개 화면에 바로 보이는 것을 확인할 수 있습니다.

### 예상 소요 시간

2일

### 완료 기준

- 로그인한 상태에서 폼으로 기록을 만들면 공개 홈, 목록, 통계에 반영된다(캐시 갱신 후 새로고침 기준으로 확인).
- 잘못된 입력은 필드별 오류로 보이고 노션에 행이 생기지 않는다.
- 같은 기록이 두 번 만들어지지 않는다(제출 연타 확인).
- 360px에서 가로 스크롤이 없고 라이트·다크 모두 읽힌다.

## Phase 4: 수정·삭제

**상태**: 미착수

### 할 작업

- 수정 폼(입력 폼 재사용), 저장 시 노션의 마지막 수정 시각을 비교해 그 사이 노션에서 바뀐 경우 충돌을 알립니다.
- 삭제는 노션 휴지통으로 보내고, 삭제 전 확인 단계를 둡니다.
- 수정·삭제 뒤 캐시 갱신

### 왜 이 순서인지

입력 폼과 쓰기 계층을 재사용하므로 입력 뒤에 둡니다. 삭제는 되돌릴 수 있도록 휴지통 방식으로만 합니다.

### 예상 소요 시간

2일

### 완료 기준

- 수정한 내용이 공개 화면에 반영된다.
- 노션에서 먼저 수정된 기록을 저장하려 하면 충돌 안내가 나오고 덮어쓰지 않는다.
- 삭제한 기록이 공개 화면에서 사라지고 노션 휴지통에서 복구할 수 있다(`in_trash` 확인).
- 확인 없이 삭제되지 않는다.

## Phase 5: 제외 행 고치기

**상태**: 미착수

### 할 작업

- 제외된 기록 안내(공개 화면)와 관리자 화면에서 해당 기록의 수정 화면으로 이동하는 경로
- 제외 사유(날짜 없음, 소요시간 형식 오류 등)에 해당하는 필드를 강조합니다. 입력 원문은 수정 화면의 입력칸에만 채워 보여 주고 제외 목록에는 사유만 보여 줍니다. 수정 화면을 열 때 인증 후 해당 페이지 한 건을 노션에서 직접 조회하며(캐시하지 않음), id 형식과 러닝 기록 data source 소속을 확인합니다.
- 고친 뒤 제외 안내에서 사라지는지 확인

### 왜 이 순서인지

v1에서 가장 아쉬웠던 점(입력 오타로 행이 제외됨)을 직접 해결하는 단계입니다. 수정 화면이 있어야 만들 수 있으므로 Phase 4 뒤에 둡니다.

### 예상 소요 시간

1일

### 완료 기준

- 제외된 기록에서 수정 화면으로 이동할 수 있고, 사유에 해당하는 필드가 강조된다.
- 고친 기록이 제외 안내에서 사라지고 목록에 나타난다.
- 입력 원문은 로그인한 관리자의 수정 화면 입력칸에만 보이고, 제외 목록과 공개 화면에는 나오지 않는다.
- 수정 화면의 단건 조회는 id 형식이 맞지 않거나 러닝 기록 data source의 페이지가 아니면 거부한다.

## Phase 6: 마무리·배포

**상태**: 미착수

### 할 작업

- `security-checker` 점검과 발견 사항 처리(쓰기 경로 CSRF, 로그인 제한, 로그에 입력값·키가 남지 않는지, 오류 화면의 내부 정보 노출)
- Vercel 환경 변수에 쓰기 키와 인증 비밀값 등록(읽기 키와 분리, 값은 콘솔에만, 쓰기 키는 Production에만 등록하고 Preview에는 등록하지 않음)
- 배포 후 로그인, 입력, 수정, 삭제 확인
- 아이폰 홈 화면 앱(standalone)에서 로그인 세션이 유지되는지 실기기 확인
- README, CLAUDE.md, PRD 갱신

### 왜 이 순서인지

쓰기 기능은 공개 인터넷에 노출되므로 배포 직전에 보안 점검을 한 번 더 하고, 실제 배포 환경에서 인증과 쓰기를 확인해야 합니다.

### 예상 소요 시간

1.5일

### 완료 기준

- 배포 URL에서 로그인한 상태로만 입력·수정·삭제가 되고, 비로그인으로는 거부된다.
- 쓰기 키와 인증 비밀값이 브라우저 소스와 저장소에 없다(패턴 검색으로 확인).
- Preview 배포에서는 관리자 쓰기가 설정 오류로 거부된다.
- 아이폰 홈 화면 앱에서 로그인 세션이 유지된다.
- 배포 환경 로그에 노션 호출 제한 오류나 입력값 노출이 없다.
- 문서가 현재 구현과 일치한다.

## 열린 질문과 리스크

### 인증 방식 비교 (Phase 1에서 결정)

| 방식 | 장점 | 단점 |
|---|---|---|
| 환경 변수 비밀번호 + 쿠키 세션 | 패키지가 적고 이해하기 쉽습니다 | 표준 인증을 배울 기회가 적고, 직접 구현한 세션의 보안 책임이 있습니다 |
| Auth.js + OAuth(허용 이메일 1개) | 실무에서 많이 쓰는 방식이라 학습 가치가 큽니다 | 새 패키지와 OAuth 앱 등록이 필요하고 설정이 복잡합니다 |
| 배포 플랫폼의 보호 기능 | 코드가 거의 필요 없습니다 | 요금제에 따라 쓸 수 있는지 확인이 필요하고, 앱 로직과 분리되어 학습 가치가 낮습니다(추정, 확인 필요) |

### 생각해볼 점

- **실제 가치**: 혼자 쓰는 앱이라면 핵심 가치는 "폰에서 바로 입력"과 "입력 검증"입니다. v1에서 소요시간 `12:5` 같은 오타로 행이 제외되던 문제를 폼 검증이 근본적으로 해결합니다.
- **노션의 특성**: 트랜잭션이 없어 부분 실패를 되돌릴 수 없으므로 멱등 키(외부ID)로 중복을 막습니다. 호출 제한은 평균 초당 3회입니다. 노션 앱에서도 수정할 수 있어 동시 수정 충돌이 가능합니다.
- **캐시 지연**: 쓰기 직후 공개 화면이 최대 약 1~2분 늦게 반영되는 것을 제출 직후의 캐시 갱신으로 줄입니다.
- **범위 관리**: 학습 과정이므로 Phase 1~3(인증, 쓰기 계층, 입력)만으로도 쓸 수 있습니다. 수정·삭제와 제외 행 고치기는 뒤에 두어 중간에 멈춰도 가치가 남게 했습니다.
- **PWA**: 관리자 화면도 모바일 우선입니다. 갤럭시는 v1에서 확인하지 않았으므로 v2에서도 같은 한계가 있습니다.

### 범위 밖 후보

- 관리자 대시보드(데이터 품질 현황)와 수동 캐시 갱신 버튼
- 나이키 런 클럽 등 외부 앱 기록 가져오기(PRD 10장)
- 오프라인 캐시와 푸시 알림(PRD 10장)
