# ROADMAP v2: Run Log 관리자 페이지

> MVP(v1) 로드맵은 [roadmaps/ROADMAP-v1.md](roadmaps/ROADMAP-v1.md)에 보관되어 있습니다.

## 개요

- **목적**: 노션 앱을 열지 않고 웹에서 러닝 기록을 안전하게 입력·수정·삭제하고, 입력 오류로 목록에서 제외되는 행을 없앱니다.
- **v1의 결과**: 읽기 전용 MVP가 2026-11-05에 완료되어 https://pjt-run-log.vercel.app 에 배포되어 있습니다. 기록 목록·상세, 주간·월간 통계, PWA 설치를 지원하며 노션 호출은 서버에서만 합니다.
- **PRD와의 관계**: v1 PRD 6장은 "로그인·인증"과 "웹에서 기록 입력·수정·삭제"를 MVP 제외 항목으로 정했습니다. v2는 이 둘을 범위에 넣으므로 PRD를 v2로 새로 작성하고 v1은 [prds/PRD-v1.md](prds/PRD-v1.md)에 보관합니다(Phase 0 결정). 기능 자체의 명세는 현재 [PRD.md](PRD.md)를 기준으로 합니다.
- **개발 원칙**: 인증 → 쓰기 계층 → 입력 → 수정·삭제 → 제외 행 고치기 순서로 진행합니다. 인증 없이 쓰기 기능을 배포하지 않습니다. 공개 조회(읽기 전용 키)와 관리자 쓰기(별도 키)는 노션 키와 코드 경로를 분리합니다.
- **소요 시간**: 1인 개발 기준의 대략적인 추정치(일 단위)이며, 실제 진행에 따라 조정합니다.
- **상태 표시**: ✅ 완료(확인 완료된 항목만), 진행 중, 미착수로 구분합니다. 직접 확인하지 않은 항목은 ✅를 쓰지 않습니다.
- **v1에서 넘어온 미확인·한계**
  - 갤럭시(Chrome, Samsung Internet) 설치와 안드로이드 "앱 설치" 버튼은 확인하지 않았습니다.
  - `lib/api/response.ts`의 응답 형식(`apiSuccess`, `apiFailure`)은 API 라우트가 없어 실제 응답으로 확인하지 못했습니다. Phase 2에서 다룹니다. (해소: Phase 2, PR #64에서 실제 응답으로 확인)
  - 상세 화면(`/runs/[id]`)은 목록 캐시를 거치지 않고 노션 전체 기록을 직접 조회해, 존재하지 않는 서로 다른 주소를 요청할 때마다 노션 호출이 생깁니다. 상세도 공유 캐시를 쓰도록 바꾸기로 했고(Phase 0 결정), Phase 2의 첫 작업에서 반영합니다. (해소: Phase 2, PR #59에서 공유 캐시로 전환)

**상태**: ✅ 완료 (2026-11-05 확인)

### 할 작업

- ✅ PRD 변경 방식 결정: 기존 `docs/PRD.md`의 제외 항목(로그인·인증, 웹 입력·수정·삭제)을 고칠지, v2용 PRD를 새로 둘지 사용자가 정합니다. 결정 전에는 PRD를 수정하지 않습니다. (V2-P0-1, 방식 B 선택: v1 PRD는 `docs/prds/PRD-v1.md`로 보관하고 `docs/PRD.md`를 v2로 새로 작성, PR #50)
- ✅ 테스트 전략 결정: 현재 테스트 러너가 없습니다. 쓰기 기능은 위험이 커서 최소한 입력 검증 함수의 단위 테스트를 도입할지 정합니다(도입하면 새 패키지 승인 필요). (V2-P0-4, Node 내장 `node --test`로 결정, 이 PC의 Node 24.20.0에서 `.ts` 테스트 실행을 직접 확인, 새 패키지 없음)
- ✅ 노션 키 분리 설계: 공개 조회용 읽기 전용 키는 그대로 두고, 관리자 쓰기용 키를 별도 환경 변수로 둡니다. 통합 권한은 필요한 만큼만 엽니다(읽기, 삽입, 수정). (V2-P0-4, 별도 통합과 `NOTION_ADMIN_API_KEY`, `lib/notion/admin/` 분리와 ESLint 제한, Vercel은 Production에만 등록. 필요한 권한은 노션 공식 문서로 확인함: 읽기는 Read content, 속성 수정과 휴지통 이동은 Update content, 페이지 생성은 Insert content. 호출 제한은 연결별이며 무료 플랜은 분당 180회(평균 초당 3회), 노션 JS SDK가 429의 Retry-After를 기다려 재시도)
- ✅ v1 알려진 한계 처리 방침: 상세 화면이 목록 캐시를 쓰도록 바꿀지(노션 호출 증폭 해소, 새 기록이 상세에서 최대 약 1분 늦게 열릴 수 있음), 형식 검사만 넣을지, 그대로 둘지 정합니다. (V2-P0-3, 상세도 공유 캐시를 쓰기로 결정, 구현은 Phase 2 첫 작업)
- ✅ 관리자 화면에서 제외된 행의 입력 원문을 보여 줄지 정합니다(PRD 4장은 공개 화면에서 원문을 숨기도록 했지만, 고치려면 관리자에게는 원문이 필요합니다). (V2-P0-2, 로그인한 관리자의 수정 화면 입력칸에만 보여 주고 공개 DTO와 공유 캐시에는 넣지 않음)

### 왜 이 순서인지

관리자 페이지는 PRD가 제외한 범위를 다루므로, 요구사항과 안전 조건을 먼저 문서로 확정해야 이후 Phase의 완료 기준이 흔들리지 않습니다. 쓰기 키 분리와 테스트 방식은 Phase 2의 구조를 정하는 전제입니다.

### 완료 기준

- ✅ PRD 변경 방식이 정해지고 그에 따라 문서가 갱신되었다(사용자 승인 후). (2026-11-05 확인, 방식 B를 사용자가 선택하고 변경안 승인 후 PR #50으로 v2 PRD 작성과 v1 보관 머지)

## Phase 2: 쓰기 계층

**상태**: ✅ 완료 (2026-11-10 확인)

### 할 작업

- ✅ 상세 화면(`/runs/[id]`)이 `loadRunRecords()`의 공유 캐시에서 기록을 찾도록 바꿉니다(`lib/runs/load.ts`에 단건 조회 추가, 약 0.25일). 이때 `CLAUDE.md`의 "상세는 직접 조회" 문장과 README의 알려진 한계 절도 고칩니다. (PR #59, 서로 다른 가짜 id 3개 요청 시 노션 호출 수정 전 3회에서 수정 후 0회, 문서도 함께 수정)
- ✅ 쓰기 전용 노션 키를 별도 환경 변수(`NOTION_ADMIN_API_KEY`)로 읽는 서버 전용 모듈을 `lib/notion/admin/`에 만들고(`server-only`), ESLint `no-restricted-imports`로 관리자 영역 밖에서 이 모듈을 import하지 못하게 막습니다. (PR #60, 위반 import 3종이 lint 오류로 차단되고 허용 위치 2종은 통과. 로컬에서는 기존 개발용 통합 키를 같은 값으로 사용)
- ✅ `lib/notion/mapper.ts`의 읽기 함수(`readTitle`, `readDate` 등)를 공유 모듈로 분리해 관리자 단건 조회와 쓰기 검증에서 재사용합니다. (PR #61, `lib/notion/readers.ts`, 분리 전후 가짜 페이지 15종의 출력이 바이트 단위로 같음)
- ✅ `package.json`에 `test` 스크립트(`node --test`)를 추가하고 입력 검증 함수를 단위 테스트합니다. 테스트 대상 모듈은 `@/` 별칭 대신 상대 경로로 import하며 새 패키지는 설치하지 않습니다. (PR #61·#62, `npm test` 86건, 변이 시험으로 테스트가 잘못된 구현을 감지함을 확인. 상대 경로는 `.ts` 확장자를 쓰고 `tsconfig`에 `allowImportingTsExtensions` 추가)
- ✅ Repository: 페이지 생성, 수정, 휴지통 이동 (PR #63, 실제 노션에서 생성·수정·휴지통 이동과 `in_trash: true` 확인, 수정·휴지통 전에 러닝 기록 DB 소속 확인을 추가)
- ✅ 입력 검증(zod 4): 읽기 쪽 규칙을 공유합니다(`lib/notion/duration.ts`의 `parseDurationToSeconds`, `lib/notion/date.ts`의 `normalizeNotionDate`, 거리는 숫자). (PR #62, 통과한 입력 16종을 노션 쓰기 형태에서 읽기 형태로 왕복해 모두 제외되지 않고 같은 값으로 읽힘, 거리는 0보다 큰 값만 허용)
- ✅ 입력 DTO와 쓰기 Service, 실패는 `AppError`로 변환 (PR #63, 실패는 `NOTION_WRITE_FAILED` 502, 로그에 입력값·오류 메시지·키가 남지 않음)
- ✅ 응답 형식(`apiSuccess`, `apiFailure`)을 실제로 사용하고 응답으로 확인합니다(v1에서 못 닫은 항목). (PR #64, `POST /api/admin/runs`의 실제 201·200·400·401·403·413 응답으로 확인)
- ✅ 외부ID 필드(PRD 4장)로 중복 입력을 막는 방법 검토 (PR #62~#64, 폼의 고유 키를 `web-<UUID>`로 외부ID에 저장하기로 결정하고, 같은 키 재전송이 200 `created: false`와 같은 id로 돌아오며 노션 행이 늘지 않음을 실제 노션에서 확인)
- ✅ 노션 쓰기 검증은 사용자 확인 후 `TEST-` 행으로만 하고, 끝나면 휴지통으로 보내 `in_trash`를 확인합니다. (V2-P2-6, 사용자 승인 후 `TEST-P2-6` 행 1개로 생성·수정·휴지통 이동, `in_trash: true`, 노션 행 수와 공개 목록이 기준값으로 복귀)

### 왜 이 순서인지

화면보다 쓰기 규칙을 먼저 정해야 입력 폼이 검증과 오류 처리를 중복해서 만들지 않습니다. 읽기와 같은 검증 규칙을 공유해야 "입력은 통과했는데 목록에서 제외되는 기록"이 생기지 않습니다.

## 열린 질문과 리스크

### 인증 방식 비교 (Phase 1에서 결정)

| 방식 | 장점 | 단점 |
|---|---|---|
| 환경 변수 비밀번호 + 쿠키 세션 | 패키지가 적고 이해하기 쉽습니다 | 표준 인증을 배울 기회가 적고, 직접 구현한 세션의 보안 책임이 있습니다 |
| Auth.js + OAuth(허용 이메일 1개) | 실무에서 많이 쓰는 방식이라 학습 가치가 큽니다 | 새 패키지와 OAuth 앱 등록이 필요하고 설정이 복잡합니다 |
| 배포 플랫폼의 보호 기능 | 코드가 거의 필요 없습니다 | 요금제에 따라 쓸 수 있는지 확인이 필요하고, 앱 로직과 분리되어 학습 가치가 낮습니다(추정, 확인 필요) |

### 생각해볼 점

- **실제 가치**: 혼자 쓰는 앱이라면 핵심 가치는 "폰에서 바로 입력"과 "입력 검증"입니다. v1에서 소요시간 `12:5` 같은 오타로 행이 제외되던 문제를 폼 검증이 근본적으로 해결합니다.
- **노션의 특성**: 트랜잭션이 없어 부분 실패를 되돌릴 수 없으므로 멱등 키(외부ID)로 중복을 막습니다. 호출 제한은 평균 초당 3회입니다. 노션 앱에서도 수정할 수 있어 동시 수정 충돌이 가능합니다.
- **캐시 지연**: 쓰기 직후 공개 화면이 최대 약 1~2분 늦게 반영되는 것을 제출 직후의 캐시 갱신으로 줄입니다.
- **범위 관리**: 학습 과정이므로 Phase 1~3(인증, 쓰기 계층, 입력)만으로도 쓸 수 있습니다. 수정·삭제와 제외 행 고치기는 뒤에 두어 중간에 멈춰도 가치가 남게 했습니다.
- **PWA**: 관리자 화면도 모바일 우선입니다. 갤럭시는 v1에서 확인하지 않았으므로 v2에서도 같은 한계가 있습니다.

### 범위 밖 후보

- 관리자 대시보드(데이터 품질 현황)와 수동 캐시 갱신 버튼
- 나이키 런 클럽 등 외부 앱 기록 가져오기(PRD 10장)
- 오프라인 캐시와 푸시 알림(PRD 10장)
